## Purpose

Create a decision-ready PRD by chaining problem framing, requirements definition, and story scaffolding.

Use it when scoping a feature, initiative, or product change that must move smoothly from strategy to delivery.

Produces a structured PRD plus core personas, requirements, and initial implementation-ready stories.

## Input

Bring the subject:

- **Works best with:** a feature, initiative, or product change (e.g. `Team inbox redesign for faster triage in customer support`)
- **Also useful:** constraints, known personas, or success signals

Zero input is fine — the flow elicits it — but a concrete subject focuses the run.

Example: `Use write-prd: Team inbox redesign for faster triage in customer support`

## Key Concepts

### Chained Skills

`problem-statement` (problem context) → `proto-persona` (user assumptions) → `prd-development` (full document) → `user-story` (initial stories) → `user-story-splitting` (split large items). Run in order; each feeds the next.

### Quality Bar

Scope boundaries validated before requirements; success criteria measurable and outcome-tied; at least one anti-pattern called out in risks.

## Application

1. Define the problem context with `problem-statement`.
2. Align user assumptions with `proto-persona`.
3. Build the full document with `prd-development`, validating scope boundaries first.
4. Draft initial stories with `user-story`; split large items with `user-story-splitting`.
5. Verify checkpoints: measurable outcome-tied success criteria, one anti-pattern in risks.

Next steps: sequence delivery (roadmap planning) or prioritize if scope exceeds capacity.

## Examples

## Common Pitfalls

- **Writing requirements before scope boundaries.** Consequence: sprawling PRD that can't be estimated. Fix: validate boundaries first.
