## Purpose

Guide the user through manual acceptance testing of recently built features. The USER performs all testing; the agent generates the checklist, guides each test, and captures issues into the phase-scoped UAT file.

Use it after completing a plan to validate that what was built actually works from the user's perspective.

## Input

Optionally bring scope:

- **Works best with:** a phase or plan number (e.g. `4`, `04-02`) — otherwise the most recently completed plan is tested
- **Also useful:** nothing else; scope resolves from `.paul/STATE.md` + `.paul/ROADMAP.md`

Example: `Use paul-verify: 04-02`

## Key Concepts

### Framework Sources of Truth

**Other harnesses.** These paths assume a Claude Code install at `~/.agents/paul-framework/`; any harness can read them there. If that directory is absent, read the same subpaths under `~/.agents/paul-framework/`. If neither exists, tell the user to install the PAUL framework (workflows/, templates/, references/) and stop — don't reinvent the workflow from memory.

- `~/.agents/paul-framework/workflows/verify-work.md` — workflow to follow
- `~/.agents/paul-framework/templates/UAT-ISSUES.md` — issue file template

### Anti-Patterns

No automated tests (CI covers that). No assumed results — the USER reports outcomes. Walk every test; log everything reported; fix nothing during testing (capture for later).

### pstack Verification Backing (automatic)

pstack is present when `.paul/pstack-models.md` or the global `~/.agents/pstack-models.md` exists, or the `poteto-mode` skill is invocable in this session. If present, check whether the project has a project-local verification skill (a `verify-*` skill generated by `/create-verification-skill`). If the user wants one, offer `/create-verification-skill` so future plans can drive the real app as part of APPLY's Qualify step. Do not run automated verification during UAT itself; the USER still performs the tests.

## Application

1. Follow `verify-work.md`: identify scope (given or most recent SUMMARY), extract testable deliverables, generate the checklist from acceptance criteria.
2. Guide the user through each test via questions; capture pass/fail/partial/skip per test.
3. Log issues to `.paul/phases/XX-name/{plan}-UAT.md`; present summary with verdict and next steps.
4. Verify success criteria:
   - [ ] Test scope identified from SUMMARY.md
   - [ ] Checklist generated based on deliverables
   - [ ] User guided through each test
   - [ ] All test results captured
   - [ ] Issues logged to `{plan}-UAT.md`
   - [ ] Summary presented with verdict
   - [ ] User knows next steps

## Common Pitfalls

- **Fixing during testing.** Consequence: untested scope creep mid-verification. Fix: capture issues, fix via plan-fix later.
